─────────────────────────────────────────
01. WHAT TAILORBOOK IS
─────────────────────────────────────────

TailorBook is an offline-first mobile application designed exclusively for
Nigerian tailors and fashion designers. It is a private, single-user business
management tool — NOT a customer-facing app. The tailor uses it to:

  • Register and manage customer profiles (name, phone, notes)
  • Create and track jobs (outfit orders) with 6-stage production pipelines
  • Store per-customer body measurements using outfit-specific templates
  • Track financial data per job (price, deposit paid, outstanding balance)
  • Receive local notifications for overdue, due-today, and due-soon jobs
  • Attach sample reference photos to jobs (camera or gallery)

All data is stored locally on the device using SQLite. There is no backend,
no authentication, no accounts, no sync in v1.0. The app is a "digital
customer book" replacing handwritten notebooks.

Target user: A Nigerian tailor with 10–200 customers, likely using WhatsApp
for customer communication. The app augments but does not replace WhatsApp.

02. PRODUCT VISION SUMMARY
─────────────────────────────────────────

From PRODUCT_VISION.txt (user-provided):

  Core philosophy: "Built for tailors, not tech people."
  
  Offline-first: Full functionality with zero internet connection.
  Privacy-first: All data stays on the tailor's device.
  
  Two delivery types (planned, not yet implemented):
    - Pickup: Customer comes to collect
    - Waybill: Tailor ships via courier (address required)
  
  Communication: WhatsApp is the channel for customer comms.
    TailorBook generates/pre-fills messages but doesn't send them.
  
  Guided workflows: App should guide the tailor through job creation
    step-by-step, not dump a form on them.
  
  Monetization model (planned):
    - Free tier: Core features (current build is effectively free tier)
    - Premium tier: AI features, cloud backup, advanced analytics
  
  AI roadmap (premium):
    - AI measurement suggestions from customer photos
    - Smart delivery date recommendations based on workload
    - Automated WhatsApp message drafting
  
  Cloud backup (premium):
    - Optional, encrypted, tailor-owned
    - Restore to new device

06. TYPESCRIPT TYPE DEFINITIONS (src/types/index.ts)
─────────────────────────────────────────

All shared types live in a single file. No barrel exports needed as all are
imported directly.

--- Customer ---

interface Customer {
  id: string;               // Generated ID: Date.now().toString(36) + random
  name: string;             // Full name
  phone: string;            // Phone number (stored as-is, formatted on display)
  notes?: string;           // Free-text notes about the customer
  avatar: string;           // One of 10 hex color strings (for avatar background)
  createdAt: string;        // ISO 8601 datetime string
}

--- Job ---

interface Job {
  id: string;
  customerId: string;       // FK → Customer.id
  customerName: string;     // Denormalized for display performance (no joins needed)
  outfitType: OutfitType;   // One of 10 outfit type strings
  style?: string;           // Optional style description (e.g. "Classic Agbada")
  fabric?: string;          // Optional fabric type (e.g. "Cashmere", "Ankara")
  deliveryDate: string;     // ISO date string "YYYY-MM-DD"
  status: JobStatus;        // One of 6 status strings
  price: number;            // Total price in Naira (integer)
  deposit: number;          // Amount deposited in Naira (integer)
  balance: number;          // price - deposit (computed, stored for query perf)
  measurementId?: string;   // Optional FK → Measurement.id
  samplePhotoUri?: string;  // Local file URI for reference photo
  notes?: string;           // Free-text instructions
  createdAt: string;        // ISO 8601 datetime string
}

--- Measurement ---

interface Measurement {
  id: string;
  customerId: string;              // FK → Customer.id
  template: MeasurementTemplate;  // Template key string
  data: Record<string, string>;   // Field values: { bust: "38", waist: "32", ... }
                                   // STORED AS JSON STRING in SQLite
  label?: string;                 // Optional human label
  createdAt: string;
}

--- AppNotification ---

interface AppNotification {
  id: string;
  type: NotificationType;   // 'overdue' | 'due_today' | 'due_soon' |
                            // 'completed' | 'payment' | 'system'
  title: string;
  message: string;
  jobId?: string;           // Optional FK → Job.id (for deep-link on tap)
  read: boolean;
  createdAt: string;
}

--- Type Aliases ---

type JobStatus = 'Pending' | 'Cutting' | 'Sewing' | 'Finishing' | 'Ready' | 'Delivered';

type OutfitType = 'Agbada' | 'Senator' | 'Suit' | 'Shirt' | 'Trouser' |
                 'Gown' | 'Kaftan' | 'Skirt' | 'Blouse' | 'Other';

type MeasurementTemplate = 'mens_senator' | 'agbada' | 'suit' |
                           'womens_gown' | 'shirt' | 'trouser';

type NotificationType = 'overdue' | 'due_today' | 'due_soon' |
                        'completed' | 'payment' | 'system';

07. DATABASE SCHEMA (SQLite / expo-sqlite)
─────────────────────────────────────────

Database name: tailorbook.db
Mode: WAL (Write-Ahead Logging) — enabled on init for better concurrency
Opened via: SQLiteProvider from expo-sqlite (async API, SDK 51+)

--- TABLE: customers ---

CREATE TABLE IF NOT EXISTS customers (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  phone TEXT NOT NULL,
  notes TEXT,
  avatar TEXT NOT NULL DEFAULT '#4B3FA0',
  createdAt TEXT NOT NULL
);

--- TABLE: measurements ---

CREATE TABLE IF NOT EXISTS measurements (
  id TEXT PRIMARY KEY,
  customerId TEXT NOT NULL,
  template TEXT NOT NULL,
  data TEXT NOT NULL,       -- JSON.stringify(Record<string, string>)
  label TEXT,
  createdAt TEXT NOT NULL,
  FOREIGN KEY (customerId) REFERENCES customers(id) ON DELETE CASCADE
);

INDEX: CREATE INDEX IF NOT EXISTS idx_measurements_customer
       ON measurements(customerId);

--- TABLE: jobs ---

CREATE TABLE IF NOT EXISTS jobs (
  id TEXT PRIMARY KEY,
  customerId TEXT NOT NULL,
  customerName TEXT NOT NULL,   -- Denormalized
  outfitType TEXT NOT NULL,
  style TEXT,
  fabric TEXT,
  deliveryDate TEXT NOT NULL,   -- "YYYY-MM-DD"
  status TEXT NOT NULL DEFAULT 'Pending',
  price REAL NOT NULL DEFAULT 0,
  deposit REAL NOT NULL DEFAULT 0,
  balance REAL NOT NULL DEFAULT 0,
  measurementId TEXT,
  samplePhotoUri TEXT,
  notes TEXT,
  createdAt TEXT NOT NULL,
  FOREIGN KEY (customerId) REFERENCES customers(id) ON DELETE CASCADE
);

INDEXES:
  CREATE INDEX IF NOT EXISTS idx_jobs_customer ON jobs(customerId);
  CREATE INDEX IF NOT EXISTS idx_jobs_status ON jobs(status);
  CREATE INDEX IF NOT EXISTS idx_jobs_delivery ON jobs(deliveryDate);

--- TABLE: notifications ---

CREATE TABLE IF NOT EXISTS notifications (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,
  title TEXT NOT NULL,
  message TEXT NOT NULL,
  jobId TEXT,
  read INTEGER NOT NULL DEFAULT 0,   -- SQLite boolean: 0=false, 1=true
  createdAt TEXT NOT NULL
);

INDEX: CREATE INDEX IF NOT EXISTS idx_notifications_read
       ON notifications(read);

--- CASCADE BEHAVIOR ---
Deleting a customer cascades to delete their measurements and jobs.
(This is enforced at the SQLite FK level via ON DELETE CASCADE)

--- IMPORTANT: FK enforcement ---
SQLite foreign keys are OFF by default. The database init runs:
  PRAGMA foreign_keys = ON;
to enable cascade deletes.

08. DATABASE API FUNCTIONS (src/utils/database.ts)
─────────────────────────────────────────

All functions are async. They use expo-sqlite's async API (SDK 51+).
All functions call getDb() which returns a cached SQLiteDatabase instance.

File path: src/utils/database.ts

--- INITIALIZATION ---

initDatabase(): Promise<void>
  Opens the DB, enables WAL and FK pragmas, creates all 4 tables and indexes.
  Called once from App.tsx on mount.

--- CUSTOMER FUNCTIONS ---

createCustomer(customer: Customer): Promise<void>
  INSERT INTO customers
  Fields: id, name, phone, notes, avatar, createdAt

getAllCustomers(): Promise<Customer[]>
  SELECT * FROM customers ORDER BY name ASC
  Returns all customers sorted alphabetically.

getCustomerById(id: string): Promise<Customer | null>
  SELECT * FROM customers WHERE id = ?

updateCustomer(id, updates: Partial<Customer>): Promise<void>
  Dynamic UPDATE: only updates provided fields using Object.keys()
  Uses parameterized queries to prevent SQL injection.

deleteCustomer(id: string): Promise<void>
  DELETE FROM customers WHERE id = ?
  Cascade deletes measurements and jobs via FK.

searchCustomers(query: string): Promise<Customer[]>
  SELECT * FROM customers WHERE name LIKE ? OR phone LIKE ?
  Pattern: '%query%'

--- JOB FUNCTIONS ---

createJob(job: Job): Promise<void>
  INSERT INTO jobs (all fields)

getAllJobs(): Promise<Job[]>
  SELECT * FROM jobs ORDER BY createdAt DESC

getJobById(id: string): Promise<Job | null>
  SELECT * FROM jobs WHERE id = ?

getJobsByCustomer(customerId: string): Promise<Job[]>
  SELECT * FROM jobs WHERE customerId = ? ORDER BY createdAt DESC

updateJob(id, updates: Partial<Job>): Promise<void>
  Dynamic UPDATE on provided fields.

updateJobStatus(id: string, status: JobStatus): Promise<void>
  UPDATE jobs SET status = ? WHERE id = ?

deleteJob(id: string): Promise<void>
  DELETE FROM jobs WHERE id = ?

getDueToday(): Promise<Job[]>
  SELECT * FROM jobs WHERE deliveryDate = ? AND status != 'Delivered'
  Uses getTodayISO() for the date value.

getOverdueJobs(): Promise<Job[]>
  SELECT * FROM jobs WHERE deliveryDate < ? AND status != 'Delivered'
  Uses getTodayISO() for comparison.

searchJobs(query: string): Promise<Job[]>
  SELECT * FROM jobs WHERE customerName LIKE ? OR outfitType LIKE ? OR notes LIKE ?
  Pattern: '%query%'

--- MEASUREMENT FUNCTIONS ---

createMeasurement(measurement: Measurement): Promise<void>
  INSERT INTO measurements
  IMPORTANT: measurement.data is JSON.stringify'd before INSERT.

getMeasurementsByCustomer(customerId: string): Promise<Measurement[]>
  SELECT * FROM measurements WHERE customerId = ? ORDER BY createdAt DESC
  IMPORTANT: Each row's data field is JSON.parse'd before returning.

getMeasurementById(id: string): Promise<Measurement | null>
  SELECT * FROM measurements WHERE id = ?
  Parses data JSON on return.

deleteMeasurement(id: string): Promise<void>
  DELETE FROM measurements WHERE id = ?

--- NOTIFICATION FUNCTIONS ---

createNotification(notification: AppNotification): Promise<void>
  INSERT INTO notifications

getAllNotifications(): Promise<AppNotification[]>
  SELECT * FROM notifications ORDER BY createdAt DESC
  Maps read field: row.read === 1 → true (SQLite integer to JS boolean)

markNotificationRead(id: string): Promise<void>
  UPDATE notifications SET read = 1 WHERE id = ?

markAllNotificationsRead(): Promise<void>
  UPDATE notifications SET read = 1

deleteOldNotifications(): Promise<void>
  DELETE FROM notifications WHERE read = 1 AND createdAt < ?
  Deletes read notifications older than 30 days.

09. DATABASE WEB STUB (src/utils/database.web.ts)
─────────────────────────────────────────

Since expo-sqlite only works on native (Android/iOS), a platform-specific
stub exists for running the app in a web browser (Replit dev environment).

The stub uses localStorage as storage via a generic read/write helper.

Key design:
  • localStorage['tailorbook_customers'] = JSON.stringify(Customer[])
  • localStorage['tailorbook_jobs'] = JSON.stringify(Job[])
  • localStorage['tailorbook_measurements'] = JSON.stringify(Measurement[])
  • localStorage['tailorbook_notifications'] = JSON.stringify(AppNotification[])

The web stub exports ALL the same function signatures as database.ts.
It does NOT implement:
  - WAL mode (not applicable)
  - CASCADE deletes (handled manually in deleteCustomer)
  - SQL indexes (not applicable)

Search functions (searchCustomers, searchJobs) use Array.filter() with
.toLowerCase().includes() instead of SQL LIKE.

getDueToday() and getOverdueJobs() use JavaScript date comparisons.

IMPORTANT: The web stub persists across page reloads via localStorage,
but data is tab-isolated and not cross-device.

10. ID GENERATION STRATEGY
─────────────────────────────────────────

IDs are NOT UUID v4. They use a custom generation function in store.ts:

  const generateId = () =>
    Date.now().toString(36) + Math.random().toString(36).substr(2, 9);

Example output: "lrx9k2c4p7f3a"

Properties:
  - Roughly time-sortable (timestamp prefix)
  - ~15 characters
  - Not guaranteed collision-free (random component is only 9 chars)
  - No external library dependency

RISK: At very high creation rates (unlikely for a single tailor), ID
collisions are theoretically possible. For v1, this is acceptable.
For v2, consider using a proper UUID library.

11. ZUSTAND STORE ARCHITECTURE (src/context/store.ts)
─────────────────────────────────────────

The entire application state lives in a single Zustand store:

  export const useStore = create<AppStore>()((set, get) => ({ ... }));

No middleware (no devtools, no persist). All persistence is via SQLite.
State in memory is ephemeral — refreshed from SQLite on initialize().

Store imported in components as:
  const { customers, addJob, ... } = useStore();

─────────────────────────────────────────
12. STORE STATE SHAPE
─────────────────────────────────────────

interface AppStore {
  // Raw data arrays (loaded from SQLite)
  customers: Customer[];
  jobs: Job[];
  measurements: Measurement[];
  notifications: AppNotification[];

  // Derived/computed collections (computed from jobs array)
  dueToday: Job[];         // Jobs where deliveryDate === today AND status !== 'Delivered'
  overdueJobs: Job[];      // Jobs where deliveryDate < today AND status !== 'Delivered'
  pendingJobs: Job[];      // Jobs where status === 'Pending'
  recentJobs: Job[];       // Last 10 jobs sorted by createdAt DESC

  // UI state
  isLoading: boolean;
  unreadNotificationCount: number;

  // Actions (see section 13)
  initialize: () => Promise<void>;
  // ... all CRUD actions
}

─────────────────────────────────────────
13. STORE ACTIONS REFERENCE
─────────────────────────────────────────

--- INITIALIZATION ---

initialize(): Promise<void>
  Loads all data from SQLite into memory.
  Sets isLoading true → fetches customers, jobs, measurements, notifications
  → computes derived state → sets isLoading false.
  Also schedules all pending notification checks.
  Called from HomeScreen's useEffect on mount.

--- REFRESH ACTIONS ---

refreshCustomers(): Promise<void>
  Reloads customers from DB, updates state.

refreshJobs(): Promise<void>
  Reloads all jobs, recomputes dueToday/overdueJobs/pendingJobs/recentJobs.

refreshNotifications(): Promise<void>
  Reloads notifications, recomputes unreadNotificationCount.

--- CUSTOMER ACTIONS ---

addCustomer(data: Omit<Customer, 'id' | 'createdAt'>): Promise<Customer>
  Generates ID, timestamps, calls db.createCustomer(), updates state.
  Returns the created Customer object.

updateCustomer(id: string, updates: Partial<Customer>): Promise<void>
  Calls db.updateCustomer(), refreshes customers state.

deleteCustomer(id: string): Promise<void>
  Calls db.deleteCustomer() (cascades measurements + jobs in SQLite),
  refreshes customers, jobs, measurements state.

--- JOB ACTIONS ---

addJob(data: Omit<Job, 'id' | 'createdAt'>): Promise<Job>
  Generates ID, timestamps, calls db.createJob(), updates state.
  Returns the created Job object.
  JobCreateScreen uses navigation.replace('JobDetail', { jobId: job.id })
  after creation — replaces history so back doesn't return to create form.

updateJob(id: string, updates: Partial<Job>): Promise<void>
  Calls db.updateJob(), refreshes jobs state.

updateJobStatus(id: string, status: JobStatus): Promise<void>
  Shorthand for status-only updates. Refreshes jobs and derived state.

deleteJob(id: string): Promise<void>
  Calls db.deleteJob(), refreshes jobs state.

--- MEASUREMENT ACTIONS ---

addMeasurement(data: Omit<Measurement, 'id' | 'createdAt'>): Promise<Measurement>
  Generates ID, timestamps, calls db.createMeasurement(), updates state.
  The data field (Record<string, string>) is passed as-is to db layer,
  which handles JSON serialization.

deleteMeasurement(id: string): Promise<void>
  Removes from DB and state.

--- NOTIFICATION ACTIONS ---

markNotificationRead(id: string): Promise<void>
  Updates DB, recomputes unreadNotificationCount.

markAllRead(): Promise<void>
  Calls db.markAllNotificationsRead(), recomputes count.

--- LOOKUP SELECTORS (synchronous) ---

getCustomer(id: string): Customer | undefined
  Returns customers.find(c => c.id === id)

getJob(id: string): Job | undefined
  Returns jobs.find(j => j.id === id)

getJobsByCustomer(customerId: string): Job[]
  Returns jobs.filter(j => j.customerId === customerId)

getMeasurementsByCustomer(customerId: string): Measurement[]
  Returns measurements.filter(m => m.customerId === customerId)

─────────────────────────────────────────
14. COMPUTED/DERIVED STATE
─────────────────────────────────────────

These are computed whenever jobs changes (inside refreshJobs and initialize):

  const today = getTodayISO(); // "YYYY-MM-DD"

  dueToday    = jobs.filter(j => j.deliveryDate === today && j.status !== 'Delivered')
  overdueJobs = jobs.filter(j => j.deliveryDate < today && j.status !== 'Delivered')
  pendingJobs = jobs.filter(j => j.status === 'Pending')
  recentJobs  = [...jobs].sort((a,b) => b.createdAt.localeCompare(a.createdAt)).slice(0, 10)

unreadNotificationCount is computed whenever notifications changes:
  notifications.filter(n => !n.read).length

─────────────────────────────────────────
15. STORE INITIALIZATION FLOW
─────────────────────────────────────────

App boots → App.tsx renders NavigationContainer + Drawer
→ HomeScreen mounts → useEffect calls store.initialize()
→ initialize() sets isLoading: true
→ Parallel fetches: getAllCustomers, getAllJobs, getMeasurementsByCustomer (all),
                    getAllNotifications
→ Computes dueToday, overdueJobs, pendingJobs, recentJobs
→ Computes unreadNotificationCount
→ Schedules notifications (checkAndScheduleNotifications)
→ Sets isLoading: false

Note: There is NO loading screen or splash gate in the current build.
The HomeScreen renders with empty arrays while loading, then updates.
This can cause a brief flash of "no jobs yet" empty states.

--- Date Helpers ---

getTodayISO(): string
  Returns today's date as "YYYY-MM-DD"

addDaysISO(days: number): string
  Returns a future date as "YYYY-MM-DD"

  Formats "YYYY-MM-DD" to human display.

formatDate(isoString: string): string
  Formats a full ISO datetime string to "5 Jul 2026"
  Used for "Created" date display.

formatDateTime(isoString: string): string
  Formats to "5 Jul, 2:30 PM" — used in notification timestamps.

getDeliveryUrgency(deliveryDate: string): 'overdue' | 'today' | 'soon' | 'normal'
  'overdue' → deliveryDate < today
  'today'   → deliveryDate === today
  'soon'    → deliveryDate within 3 days of today
  'normal'  → everything else
  Used by JobListScreen for color-coded dates and JobDetailScreen for chip colors.

getFirstName(fullName: string): string
  Returns first space-delimited word.
  "Emeka Johnson" → "Emeka"

getGreeting(): string
  Time-based greeting:

    12:00–16:59 → "Good afternoon"
    17:00–23:59 → "Good evening"

formatPhone(phone: string): string
  Formats Nigerian phone numbers for display.
  "08031234567" → "0803 123 4567"
  If not 11 digits, returns as-is.

isValidName(name: string): boolean
  name.trim().length >= 2

isValidPhone(phone: string): boolean
  Strips spaces/hyphens, checks if remaining is 10–11 digits.
  Accepts: "080...", "090...", "070..." patterns.

--- Financial Helpers ---

formatNaira(amount: number): string
  Formats to "₦45,000" with thousands separator.
  Uses Intl.NumberFormat with 'en-NG' locale.

parseNaira(value: string): number

  Strips non-numeric characters.
  Returns 0 if empty/invalid.

--- Avatar Helpers ---

─────────────────────────────────────────
17. NOTIFICATION SYSTEM (src/utils/notifications.ts)
─────────────────────────────────────────

TailorBook uses LOCAL notifications only (no push server).
Notifications are scheduled on the device using expo-notifications.

--- Permissions ---

requestNotificationPermissions(): Promise<boolean>
  Requests iOS/Android notification permissions.
  Returns true if granted, false otherwise.
  Called from App.tsx on startup.

--- Scheduling ---

scheduleJobNotifications(job: Job): Promise<void>
  Schedules 3 local notifications for a job:
    1. "due_soon"  → 3 days before deliveryDate at 08:00
    2. "due_today" → on deliveryDate at 07:00
    3. "overdue"   → day after deliveryDate at 08:00 (if not delivered)
  Uses expo-notifications.scheduleNotificationAsync with trigger: { date: Date }

cancelJobNotifications(jobId: string): Promise<void>
  Cancels all scheduled notifications for a given job.
  Fetches all scheduled notifications, filters by job identifier,
  cancels matching ones.

--- Database Integration ---

checkAndScheduleNotifications(jobs: Job[]): Promise<void>
  Run on app initialize(). For each non-Delivered job:
    - Creates in-app notification records (AppNotification in SQLite)
    - Schedules OS-level local notifications
  Creates records for: overdue, due_today, due_soon based on date comparison.

Note: In-app notifications (shown in NotificationsScreen) are stored in SQLite.
OS-level notifications (lock screen banners) are handled by expo-notifications.
These are separate systems that run in parallel.

  1. JS bundle evaluates
  2. SplashScreen.preventAutoHideAsync() called (keeps splash visible)

  6. GestureHandlerRootView > NavigationContainer > RootNavigator renders
  7. Drawer renders → HomeTab is initial route → HomeScreen mounts
  8. HomeScreen useEffect: store.initialize() → loads all data from SQLite

Note: No loading state is shown between step 5 and 8.

49. CRITICAL BUGS
─────────────────────────────────────────

BUG-001: No custom date picker for delivery date
  Severity: HIGH (UX-breaking for some tailors)
  Location: JobCreateScreen.tsx, DELIVERY_PRESETS
  Description: Users can only choose from 4 preset durations (Tomorrow, 3 Days,
    1 Week, 2 Weeks). There is no free date picker. A tailor with a 3-week or
    specific calendar-date deadline has no way to input it.
  Fix: Add DateTimePicker (expo or @react-native-community/datetimepicker)
    with the presets as shortcuts and a "Custom date" option.

BUG-002: Delivery date comparison ignores timezone
  Severity: MEDIUM
  Location: helpers.ts (getTodayISO), database.ts (getDueToday, getOverdueJobs)
  Description: new Date().toISOString().split('T')[0] returns UTC date.
    In UTC+1 (Nigeria), this is wrong between midnight and 1 AM.
    A job due "today" by Nigerian time might be marked overdue at midnight.
  Fix: Use local date: new Date().toLocaleDateString('en-CA') which gives YYYY-MM-DD in local TZ.

BUG-003: Tailor name and shop name are hardcoded
  Severity: HIGH (product quality)
  Location: HomeScreen.tsx (tailorName = 'Chinedu'), DrawerContent.tsx ("Tunde Stitches")
  Description: Every tailor who installs this app sees "Chinedu" as the greeting
    and "Tunde Stitches" as their shop name in the drawer.
  Fix: AccountScreen should save tailor name + shop name to AsyncStorage or SQLite
    settings table. Read in HomeScreen and DrawerContent.

BUG-004: MeasurementFormScreen creates new record every time (no edit)
  Severity: MEDIUM
  Location: MeasurementFormScreen.tsx
  Description: Every save creates a NEW measurement record. No way to edit
    an existing measurement. Customers accumulate duplicate records.
    The existingMeasurementId param exists in the type but is unused.
  Fix: If existingMeasurementId is provided, load it and UPDATE on save
    instead of INSERT.

BUG-005: Notification scheduling does not cancel on delivery
  Severity: MEDIUM
  Location: notifications.ts, store.ts updateJobStatus
  Description: When a job status changes to 'Delivered', the OS-level
    scheduled notifications (overdue, due_today, due_soon) are not cancelled.
    The tailor may receive a banner "Job is overdue" for a delivered job.
  Fix: Call cancelJobNotifications(job.id) inside updateJobStatus() when
    newStatus === 'Delivered'.

BUG-006: Logout button is a no-op
  Severity: LOW (no auth in v1, expected)
  Location: DrawerContent.tsx
  Description: Pressing "Log out" shows an alert but does nothing.
    Since there's no authentication in v1, this is by design.
    But the UI implies it does something, which is confusing.
  Fix (short-term): Remove logout from drawer or change label to "Clear all data"
    with a destructive confirmation that actually clears the SQLite database.

BUG-007: Flash of empty state on app load
  Severity: LOW (cosmetic)
  Location: HomeScreen.tsx
  Description: store.initialize() is async. Before it completes, all lists
    (dueToday, recentJobs etc.) are empty arrays, showing empty states
    briefly even if the user has existing data.
  Fix: Track isLoading in store, show a skeleton/spinner while loading.

BUG-008: No pull-to-refresh on CustomerDetailScreen or JobDetailScreen
  Severity: LOW
  Location: CustomerDetailScreen.tsx, JobDetailScreen.tsx
  Description: Data on detail screens is read from in-memory store state.
    If the store is stale, details may not reflect latest DB state.
    Most create/update actions refresh the store, so this is rare.
  Fix: Add RefreshControl on detail screen ScrollViews.

UX-001: No confirmation when navigating away from unsaved form
  Forms (JobCreate, CustomerCreate, MeasurementForm) have no "are you
  sure you want to leave?" guard. The tailor can accidentally lose a
  half-filled form by tapping the back button.

UX-002: No "WhatsApp" quick action on CustomerDetail
  Product vision says WhatsApp is the communication channel. The app
  has a phone call link but no WhatsApp deep-link.
  Fix: Add WhatsApp button: Linking.openURL('whatsapp://send?phone=' + phone)
  or 'https://wa.me/' + internationalPhone

UX-003: Due today shows "Due today by 6:00 PM" — time is hardcoded
  Location: HomeScreen.tsx DueTodayItem
  The "by 6:00 PM" string is hardcoded. There's no time component on
  deliveryDate (it's a date string, not datetime). Remove the time or
  make it configurable.

UX-004: Balance field is calculated but the user inputs a string
  JobCreateScreen uses parseNaira() which strips non-numeric characters.
  But the user types "45000" and the displayed balance is "₦45,000".
  Edge case: What if user types "45,000" (with comma)? parseNaira strips
  commas, so it works. But "₦45,000" would also parse correctly. No harm,
  but not validated with user feedback.

UX-005: No way to search within MeasurementForm existing measurements
  If a customer has many past measurements, finding the right one to copy
  requires scrolling through the list with no search/filter.

UX-006: Customer search runs a DB query on every keystroke
  Potential performance issue on slow devices with large customer lists.
  Consider debouncing with a 200–300ms delay.

UX-007: Recent Jobs on HomeScreen shows last 10 jobs by createdAt
  Not by last-updated or by status urgency. A job created long ago but
  status-changed recently won't bubble up in recents.

UX-008: Status badge sizes ('sm' vs 'md') are inconsistent
  JobListScreen uses 'sm', JobDetailScreen uses 'md' (default).
  HomeScreen DueTodayItem uses 'sm', RecentJobCard uses a manual dot+text.
  Standardize status display across all list and detail contexts.

51. TECH DEBT ITEMS
─────────────────────────────────────────

DEBT-001: ID generation is not UUID
  Custom generateId() function. Low collision risk for single-user app
  but not production-grade. Switch to nanoid or uuid when scaling.

DEBT-002: customerName is denormalized in Job
  Job.customerName is duplicated from Customer.name. If the tailor edits
  a customer's name, all their jobs still show the old name.
  Fix: Update all jobs when customer name changes, OR join on display.

DEBT-003: No input sanitization on free-text fields
  notes, style, fabric, label — all stored as-is. Not a security issue
  (no server, no SQL injection risk since parameterized queries are used)
  but could cause display issues with very long strings or emoji.

DEBT-004: Measurements data is JSON string in SQLite
  The data field is JSON.stringify'd on write and JSON.parse'd on read.
  There's no schema enforcement. A bad parse would silently return
  null/undefined. Should add try/catch around JSON.parse.

DEBT-005: No error boundaries
  If any screen throws an uncaught error, the entire app crashes.
  React error boundaries are not implemented.

DEBT-006: HomeScreen calls initialize() on every mount
  If the user navigates away from Home and back, initialize() runs again.
  This is harmless (just reloads data) but wasteful. Add an isInitialized
  flag to the store to prevent duplicate initialization.

DEBT-007: seedData.ts exists but is not used
  The file contains seed customers and jobs for development testing.
  It's not imported anywhere. Should be removed or wired to a dev toggle.

DEBT-008: No TypeScript strict mode
  tsconfig.json has strict mode disabled or partially configured.
  Several implicit any types and non-null assertions exist.

DEBT-009: KeyboardAvoidingView behavior is 'padding' only for iOS
  Android gets `undefined` behavior which is often wrong on smaller screens.
  Should test with KeyboardAvoidingView behavior="height" on Android.

DEBT-010: AccountScreen/SubscriptionScreen/HelpScreen may be placeholder stubs
  Not confirmed to have real implementations. Likely show minimal content.

57. CLOUD BACKUP ARCHITECTURE
─────────────────────────────────────────

From product vision — optional cloud backup (premium):

Design principles:
  - Tailor-owned: Data should belong to the tailor, not TailorBook
  - End-to-end encrypted: TailorBook cannot read the backed-up data
  - Restore to new device: Full data recovery from backup

Technical approach (recommended):
  1. On backup trigger (manual or scheduled):
     - SQLite → JSON export (customers, jobs, measurements, notifications)
     - Encrypt JSON with a key derived from tailor's PIN/password
     - Upload encrypted blob to cloud storage (Cloudflare R2, S3, Supabase Storage)
  2. Backup identifier: phone number or email (tailor-chosen)
  3. Restore flow:
     - Enter backup ID + PIN on new device
     - Download encrypted blob
     - Decrypt → restore SQLite tables
  
  Storage cost: A typical tailor's database would be < 5MB even with
    hundreds of customers and jobs. Cloud storage is essentially free at this scale.

Authentication: OTP via SMS (Nigerian tailors are familiar with OTP)
  - Send OTP to tailor's phone number
  - Verify before allowing backup/restore

WhatsApp Business API is heavy (requires Facebook Business verification).
For TailorBook, the simpler "share to WhatsApp" approach is correct:

  Deep link format:
    whatsapp://send?phone={internationalPhone}&text={encodedMessage}
  
  Web fallback:
    https://wa.me/{internationalPhone}?text={encodedMessage}

Nigerian number formatting:
  Input:  "0803 123 4567" or "08031234567"
  Output: "2348031234567" (replace leading 0 with country code 234)

  const formatPhoneInternational = (phone: string): string => {
    const digits = phone.replace(/\D/g, '');
    if (digits.startsWith('0')) return '234' + digits.slice(1);
    if (digits.startsWith('234')) return digits;
    return '234' + digits;
  };
